## 目的

決策表（Decision Table）是將業務規則系統化的工具：給定一組條件（Criteria），應產生什麼預期行為（Action）？

它是驗收條件（AC）與具體測試案例之間的橋樑。目標不是窮舉所有排列組合，而是識別**有價值、高風險的組合**，精確記錄預期的業務邏輯，並讓領域專家能夠 Review。

## 適用範圍

決策表適合：
- **條件組合邏輯**：折扣規則、定價分層、權限判斷、資格檢查
- **邊界值測試**：「至少 X 件」、「超過 Y 元」、「介於 A 到 B 之間」
- **多物件交互**：購物車多品項組合、多用戶角色、多優惠疊加

**不適合**決策表的場景：
- 效能、壓力、安全性測試
- 狀態機（State Machine）或高併發競態條件
- 以順序流程為主、沒有條件分支的工作流程

## 操作流程

### 步驟 1：釐清需求範圍

從用戶描述中提取（或直接詢問）：
- 這個功能／規則的核心業務邏輯是什麼？
- 哪些輸入變數會影響結果（條件/Criteria）？
- 結果應該產生什麼（預期行為/Action）？
- 有已知的邊界值或特殊情境嗎？
- 適用的操作介面（API、Web UI、App）？

若用戶描述簡短，可合理推斷並**明確列出假設**，讓用戶確認或修正。

### 步驟 2：定義 Criteria（條件）

列出影響結果的獨立輸入變數。每個 Criteria：
- 使用具體名稱，而非泛用的「Y / N」（例如：啤酒數量、折扣碼類型）
- 定義可能的值或範圍，聚焦於邊界值

**好的範例：**
| Criteria    | 可能值              |
|-------------|---------------------|
| 啤酒數量    | 0, 1, 5, 6, 7, 12   |
| 可樂數量    | 0, 1, 5, 6          |

**避免：**
| Criteria     | 可能值 |
|--------------|--------|
| 有買啤酒     | Y / N  |
| 有買可樂     | Y / N  |

第二種寫法隱藏了邊界值，無法驗證「剛好 6 件」vs「7 件」的邏輯差異。

### 步驟 3：定義 Action（預期結果）

精確描述每個結果，而非模糊表述：
- **有計算公式**：明確寫出公式（例如：`總優惠 = 優惠組數 × -26 元`）
- **有狀態變更**：明確命名（例如：`訂單狀態: 成立 / 拒絕`）
- **有數量限制**：明確說明上限（例如：`最大限購數量: 6 件`）

避免寫「優惠已套用」這種含糊描述——應說明優惠金額與計算方式。

### 步驟 4：定義 Rules（規則列）

每個 Rule 是決策表的一欄，代表一個有意義的條件組合。選擇原則：
- **邊界條件**：剛好低於、恰好等於、剛好超過閾值
- **空值/零值/無效值**：空購物車、數量為 0、無效折扣碼
- **正常流程（Happy Path）**：典型的成功情境
- **交互組合**：多個條件同時影響同一個 Action 的情況

不需要列出全部排列；優先挑選業務意圖明確、不同的組合。

每個 Rule 須附上：
- **測試企圖**：此組合要驗證什麼？（例如：驗證空購物車不觸發折扣）
- **重要性**：對業務邏輯的影響程度？（例如：保護商家利益、確認最大合法邊界）

### 步驟 5：輸出決策表

使用以下格式呈現：

```
## 決策表：[功能/規則名稱]

### Criteria（條件）
| Criteria       | Rule 1 | Rule 2 | Rule 3 | Rule 4 | ... |
|----------------|--------|--------|--------|--------|-----|
| [變數名稱 1]   | 值     | 值     | 值     | 值     |     |
| [變數名稱 2]   | 值     | 值     | 值     | 值     |     |

### Action（預期結果）
| Action                        | Rule 1 | Rule 2 | Rule 3 | Rule 4 | ... |
|-------------------------------|--------|--------|--------|--------|-----|
| [結果名稱]                    | 結果   | 結果   | 結果   | 結果   |     |
| 計算公式：總優惠 = 組數 × -X  | 計算值 | 計算值 | 計算值 | 計算值 |     |

### Rule 說明
|          | Rule 1 | Rule 2 | Rule 3 | Rule 4 | ... |
|----------|--------|--------|--------|--------|-----|
| 測試企圖 | 說明   | 說明   | 說明   | 說明   |     |
| 重要性   | 說明   | 說明   | 說明   | 說明   |     |
```

若 Rules 超過 8 個，考慮依情境群組拆分為多張子決策表。

### 步驟 6：邀請專家 Review

呈現決策表後，明確標記：
- 哪些 Rule 的業務邏輯你不確定（請用戶確認）
- 你所做的假設（請用戶修正）
- 可能遺漏的邊緣情況

**重要提醒**：AI 產生的決策表是起點，不是終稿。數值計算尤其容易出錯——請務必請用戶驗證公式與預期數值。決策表必須由領域專家親自 Review 後才算定案。

## 後續銜接

決策表完成後，可主動提供協助：
- 將決策表轉換為**抽象測試案例（Abstract Test Cases）**（不涉及 UI 操作細節）
- 根據「重要性」排序，建議**測試執行優先順序**
- 識別哪些 Rules 適合自動化，哪些需要手動驗證
